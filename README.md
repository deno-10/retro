# Retro

Доска для ретроспектив спринта. Один бинарник на Go без внешних зависимостей, фронт — обычный JS без сборки.

## Что умеет (итерация 1)

- Доска по ссылке, четыре шаблона колонок (Классика, Start/Stop/Continue, 4L, Mad/Sad/Glad).
- Карточки с подписью или анонимно. В фазе записи чужие карточки скрыты — на сервере, а не в браузере.
- Фазы: запись → показ → голосование → обсуждение. Переключает ведущий (создатель доски).
- Группировка карточек: после фазы записи ведущий перетаскивает карточку на другую, похожие склеиваются в группу. За группу голосуют как за одну карточку, голоса суммируются, в обсуждении группы сортируются по сумме. Группа из одной карточки распадается сама.
- Голосование точками, лимит на участника задаёт ведущий.
- Таймер фазы: ведущий запускает обратный отсчёт, его видят все. По истечении доска сама переходит к следующему этапу (запись → показ → голосование → обсуждение); на обсуждении таймер просто заканчивается. Срабатывает на сервере, даже если все закрыли вкладки; после рестарта сервера восстанавливается при первом открытии доски. Ручная смена фазы сбрасывает таймер.
- Изменения видны всем сразу (SSE), счётчик участников онлайн.
- Решения (action items): после фазы записи любой участник записывает, что сделать и кто отвечает; отметка «сделано». Правят и удаляют автор решения и ведущий.
- Экспорт доски в Markdown, включая решения чек-листом.
- История команды: в фазе обсуждения ведущий создаёт «следующее ретро» — новую доску с тем же шаблоном и лимитом голосов, куда переезжают незакрытые решения с пометкой «перенесено». Доски связаны ссылками «предыдущее / следующее», выпадающая «История» показывает всю цепочку с числом открытых решений.
- Хранение: SQLite в `data/retro.db` (драйвер `modernc.org/sqlite` на чистом Go, без CGO). Прежний JSON-файл по-прежнему поддерживается, а при первом запуске с пустой базой доски из лежащего рядом `boards.json` импортируются автоматически.

## Запуск

Нужен Go 1.26+ (с `GOTOOLCHAIN=auto` нужная версия подтянется сама).

```
go run .                                   # http://localhost:8080, данные в data/retro.db
go run . -addr 127.0.0.1:8080               # доступ только с этого компьютера
go test ./...
go build -o retro . && ./retro -addr :8080 -data /var/lib/retro/retro.db
./retro -data data/boards.json             # прежнее JSON-хранилище
```

Хранилище выбирается по расширению файла в `-data`: `.json` — JSON-файл, всё остальное — SQLite.

Создание следующего ретро сохраняет новую доску и ссылку на неё одной операцией.
Импорт из `boards.json` также атомарен: при ошибке ни одна доска не добавляется,
поэтому после устранения ошибки следующий запуск может повторить импорт целиком.

## Постоянный сервис для команды

Подготовлен комплект [развёртывания и обслуживания](deploy/README.md):
Docker Compose с автоперезапуском, Caddy с HTTPS и общим входом, постоянный
том SQLite, резервное копирование restic с проверкой восстановления,
мониторинг и уведомления, инструкции обновления и отката. Сервер, домен,
внешнее хранилище и получатель уведомлений настраиваются при размещении.

Приложение предоставляет `/healthz`, `/readyz` и `/metrics`; при ошибке запуска
возвращает ненулевой код. Для восстановления базы и управления ведущим есть
локальные команды `backup`, `verify`, `restore`, `transfer-owner`.
HTTP и SSE ограничены по нагрузке и времени записи, тексты и идентификаторы
участников не записываются в журналы запросов.

Для публичного адреса используйте Compose из инструкции: запуск одного
бинарника или прежняя команда `docker run` сами по себе не включают вход и TLS.
Общий пароль подходит доверенной команде; персональные права на доски и SSO
остаются отдельным этапом.

## Проверки

```
go test -race ./...
go vet ./...
python3 -m unittest discover -s tests/ops -v
```

Браузерные регрессионные тесты требуют Node.js 20+ и Playwright:

```
npm ci
npx playwright install chromium
npm test
npm run test:integration
```

Node.js нужен только для тестов; запуск приложения и фронтенд остаются без сборки.
`test:integration` собирает Go-бинарник, запускает его на локальном порту с временной
SQLite-базой и проверяет браузер вместе с настоящим API. После тестов сервер
останавливается, временные данные удаляются.
Интеграционные тесты запускают полноценный Chromium в headless-режиме
(`channel: 'chromium'`): он нужен для настоящего восстановления из BFCache.
Команда `playwright install chromium` устанавливает нужный браузер;
установки только `--only-shell` для этого набора недостаточно.
Тесты проверяют сохранение черновиков и конфликты редактирования, порядок
HTTP/SSE-ответов и обновление при обрыве SSE, повтор отправки без дублей,
восстановление после перезагрузки и настоящего возврата из BFCache через
«Назад/Вперёд», сохранение участника при сбое хранилища, таймауты запросов, повтор голосования,
установку отметки «сделано», атомарность создания следующего ретро и импорта,
а также гонки таймеров, отклонение действий после завершения фазы и проверку
всего JSON-тела до изменения доски. Дополнительные проверки эксплуатации
покрывают ошибку bind, готовность БД, лимиты и гонки запросов/SSE, восстановление
SQLite и роли ведущего, доставку уведомлений. Настоящие HTTPS, пароль, SSE,
перезапуск и restic проверяются [отдельным набором](deploy/README.md#локальные-регрессионные-проверки).
GitHub Actions запускает проверки и тест Compose; тег `v*` после успешных
проверок публикует версионированный образ в GHCR.

## Как провести ретро с ноутбука

Сервер слушает все сетевые интерфейсы, поэтому коллеги в одной сети (или в одном VPN) откроют доску по адресу вашего компьютера. Ничего разворачивать не нужно.

1. Запустите `go run .` (или собранный бинарник). В логе появятся строки `ссылка для команды` с адресами вида `http://192.168.1.5:8080` — это и есть ссылка для коллег. Если брандмауэр спросит, разрешите входящие подключения.
2. Откройте ссылку у себя, создайте доску, выберите шаблон и скопируйте ссылку на доску кнопкой «Скопировать ссылку». Отправьте её в чат команды. Кто создал доску, тот и ведущий.
3. **Запись.** Каждый пишет карточки, чужие скрыты. Ведущий может запустить таймер: по его концу доска сама перейдёт к показу.
4. **Показ.** Карточки открываются. Ведущий перетаскивает похожие карточки друг на друга, чтобы объединить в группы.
5. **Голосование.** Ведущий задаёт число голосов на человека, все отмечают важное. За группу голосуют как за одну карточку.
6. **Обсуждение.** Карточки отсортированы по голосам. Идите сверху вниз и записывайте решения в панели «Решения»: что сделать и кто отвечает.
7. В конце нажмите «Скачать .md» — протокол ретро с карточками, голосами и решениями. Кнопка «Следующее ретро» создаст доску для следующего спринта и перенесёт в неё незакрытые решения.

По умолчанию данные лежат в `data/retro.db` относительно текущего рабочего
каталога. Для остановки запущенного в терминале сервера нажмите Ctrl+C;
для повторного запуска используйте тот же путь `-data`. Пока ноутбук выключен,
доска недоступна; постоянный адрес настраивается по [инструкции](deploy/README.md).

Docker:

```
docker build -t retro .
docker run -d -p 8080:8080 -v retro-data:/app/data --name retro retro
```

## Структура

```

```

## API

Чтение доски, SSE и изменения требуют `X-Participant` (для SSE — параметр
`?participant=`): 8–64 символа `[A-Za-z0-9-]`, браузер генерирует его сам.
Шаблоны, история и экспорт не требуют этого ID. В постоянном размещении
все эти маршруты дополнительно защищены общим входом Caddy.

Тело JSON-запроса должно содержать ровно одно значение. После него допустимы
только пробельные символы; второе значение и посторонний текст дают `400` до
изменения данных. Ограничение 1 МиБ относится ко всему телу, включая пробелы.
В запросе таймера обязательно целое поле `minutes`: отсутствие поля и `null`
дают `400`; явное `0` останавливает таймер.

| Метод | Путь | Тело | Что делает |
|---|---|---|---|
| GET | `/api/templates` | — | список шаблонов |
| POST | `/api/boards` | `{title, template}` | создать доску; автор — ведущий |
| GET | `/api/boards/{id}` | — | доска глазами участника |
| GET | `/api/boards/{id}/events` | — | SSE: событие `board` с представлением доски на каждое изменение |
| GET | `/api/boards/{id}/export.md` | — | Markdown (после фазы записи) |
| POST | `/api/boards/{id}/phase` | `{phase}` | сменить фазу (ведущий) |
| POST | `/api/boards/{id}/vote-limit` | `{voteLimit}` | лимит голосов (ведущий) |
| POST | `/api/boards/{id}/timer` | `{minutes}` | запустить таймер фазы на 1–120 минут, `0` — остановить (ведущий) |
| POST | `/api/boards/{id}/next` | `{title}` | создать следующее ретро с переносом незакрытых решений; 201 с новой доской (ведущий, один раз) |
| GET | `/api/boards/{id}/history` | — | цепочка ретро команды от первого к последнему: `id, title, phase, createdAt, openActions, current` |
| POST | `/api/boards/{id}/cards` | `{columnId, text, author}` | добавить карточку (запись, показ) |
| PATCH | `/api/boards/{id}/cards/{cardId}` | `{text, revision}` | изменить свою карточку; ведущий — любую |
| DELETE | `/api/boards/{id}/cards/{cardId}` | — | удалить свою карточку; ведущий — любую |
| POST | `/api/boards/{id}/cards/{cardId}/vote` | `{voted}` | установить голос: `true` — поставить, `false` — снять (голосование); для карточки в группе — голос за группу |
| POST | `/api/boards/{id}/cards/{cardId}/group` | `{targetCardId}` | присоединить карточку к карточке или её группе в той же колонке (ведущий, после записи) |
| DELETE | `/api/boards/{id}/cards/{cardId}/group` | — | вынуть карточку из группы (ведущий) |
| POST | `/api/boards/{id}/actions` | `{text, assignee}` | записать решение (после фазы записи) |
| PATCH | `/api/boards/{id}/actions/{actionId}` | `{text, assignee, revision}` | изменить решение (автор, ведущий) |
| DELETE | `/api/boards/{id}/actions/{actionId}` | — | удалить решение (автор, ведущий) |
| POST | `/api/boards/{id}/actions/{actionId}/done` | `{done}` | установить отметку: `true` — сделано, `false` — не сделано (автор, ведущий) |

Ошибки: `{"error": "..."}` с кодами 400 (данные), 403 (права/запрос с другого
сайта), 404, 409 (фаза, лимит голосов/размера или конфликт изменений),
429 (ограничение запросов/соединений, с `Retry-After`).

### Версии и повтор запросов

У доски, карточки и решения есть числовая `revision`. При PATCH нужно передать
версию редактируемой карточки или решения, полученную при открытии редактора.
Если запись уже изменили, сервер возвращает 409 без перезаписи. Интерфейс
сохраняет черновик и позволяет сравнить его с актуальной записью. Версия доски
нужна клиенту для упорядочивания HTTP/SSE-ответов. Старые данные без версии
читаются как версия 0, отдельная миграция не требуется.
Если другой участник удалил редактируемую запись, её черновик остаётся
доступным в разделе «Правки удалённых записей» до явного закрытия.

Для создания карточек и решений браузер передаёт `Idempotency-Key` — случайный
идентификатор операции из 8–64 символов `[A-Za-z0-9-]`. При потере ответа нужно
повторить тот же запрос с тем же ключом. Сервер сохраняет ключ вместе с записью:
повтор не создаёт дубликат, в том числе после перезапуска. Ответ содержит
актуальное представление доски. Повторное использование ключа с другим телом
или для другого вида операции возвращает 409. Ключ действует в пределах
одной доски и одного участника; новая запись требует нового ключа.
Без заголовка создание доступно для прежних клиентов, но повтор не защищён
от дублирования. Удаление карточки или решения не удаляет запись о выполненной
операции: её повтор не восстанавливает удалённый объект.

При обновлении клиента API учтите: PATCH теперь требует `revision`, а `/done`
требует явное поле `done`. Повторная установка `done: true` оставляет решение
выполненным. `/vote` требует явное поле `voted`: повтор `voted: true` сохраняет
голос и не расходует дополнительный бюджет, повтор `voted: false` оставляет
голос снятым. Команда применяется ко всей текущей группе карточки.

### Черновики и потеря соединения

Черновики новых карточек и решений, открытые редакторы и очередь отправки
сохраняются в `sessionStorage` с привязкой к доске и участнику. Перезагрузка
в той же вкладке восстанавливает текст, ответственного и исходную версию
редактируемой записи. Это хранилище сессии вкладки, а не резервная копия
между устройствами или после её закрытия. Если браузер запрещает запись
или места не хватает, интерфейс показывает предупреждение. Повреждённый
снимок не перезаписывается автоматически: для возобновления сохранения
нужен явный сброс, который сохраняет текущий ввод в новый снимок.

При возврате через «Назад/Вперёд» страница из BFCache заново читает актуальные
черновики и очередь этой вкладки до подключения к серверу. Ответы запросов
от прежнего открытия страницы не могут удалить восстановленный текст или
вернуть уже отправленную запись. Если запись в хранилище не удалась, текст
в памяти сохраняется. При расхождении с другой сохранённой версией интерфейс
предупреждает и предлагает загрузить её только после явного подтверждения;
нужный текст из памяти следует предварительно скопировать.

Создаваемая запись и её ключ повтора сохраняются до начала HTTP-запроса.
После перезагрузки отправка повторяется только по кнопке пользователя с
прежним ключом. Успешно отправленная или явно удалённая запись убирается
из очереди. Ожидание API-ответа, включая чтение тела, ограничено 15 секундами.
При таймауте создания данные остаются для безопасного повтора. При потере
ответа PATCH редактор сохраняет черновик и сверяет его с текущей доской;
следующее сохранение требует явного разрешения неопределённого результата.

## Как устроен realtime

Клиент держит одно SSE-соединение. Изменение одной доски идёт через атомарный `store.Update`, создание следующего ретро — через `store.CreateNext`, затем вызывается `hub.Notify(boardID)`. Каждое SSE-соединение по сигналу перечитывает доску и отправляет участнику его представление `Board.View`. Доски маленькие, поэтому отправляется вся доска целиком, а не дифф. Клиент применяет и ответы HTTP, и события SSE, отбрасывая устаревшие версии доски. При обрыве SSE он периодически обновляет доску через GET до восстановления событий. Несохранённые правки хранятся отдельно от серверного состояния и переживают перерисовку. Переподключение делает сам `EventSource`; сервер шлёт комментарий-пинг раз в 25 с, чтобы прокси не рвали соединение.

Дедлайн фазы проверяется внутри транзакции до применения действия, в том числе
для первого запроса после перезапуска. Например, голос после истечения таймера
голосования отклоняется. Переход фазы сохраняется даже при отказе в запрошенном
действии; изменения отклонённой операции не сохраняются.

## Идентификация

Браузер сохраняет id участника в `localStorage` и закрепляет его за вкладкой
в `sessionStorage`. Запись проверяется повторным чтением. При отказе
`localStorage` резервная копия сохраняет участника и доступ к его черновикам
после обновления страницы. Уже открытая вкладка сохраняет свой id, даже если
в `localStorage` появился другой; чужой сохранённый id не перезаписывается.

Если id доступен только в сессии вкладки, интерфейс постоянно предупреждает
о возможной потере доступа после её закрытия. Если оба хранилища недоступны,
предупреждение сообщает о риске уже при обновлении страницы.
Это не аутентификация: после общего входа участником становится знающий ссылку.
Ведущий — создатель доски с тем же id. Администратор может восстановить его
роль через [transfer-owner](deploy/README.md#восстановление-ведущего).
SSO и индивидуальные права — следующая итерация.

## Дальше

1. Postgres (`jsonb`) как ещё одна реализация `Store` — для нескольких реплик, вместе с внешним pub/sub вместо хаба в памяти. SQLite уже есть: таблица `boards(id, data, created_at, updated_at)`, доска — JSON-документ.
2. SSO по OIDC (Okta / Azure AD / Keycloak): участник = `sub` из токена, роль ведущего переживает смену браузера.
3. Команды как сущность: имя, список участников, все цепочки ретро команды на одной странице. Сейчас команда — это цепочка досок, вход в неё по ссылке на любую из них; с SSO цепочки лягут в команды без переделки.

## Ограничения

- Один инстанс: подписки живут в памяти процесса. Для нескольких реплик нужны общая база и внешний pub/sub; одних липких сессий недостаточно.
- SQLite — файл на одном узле: несколько реплик с общей базой невозможны, для этого нужен Postgres.
- В режиме `.json` файл переписывается целиком при каждом изменении — для десятков досок это незаметно, для тысяч используйте SQLite.
- Тексты карточек никак не модерируются; максимум 2000 символов.
- 1000 досок на экземпляр; 500 карточек, 200 решений, 5000 ключей повтора и
  4 МиБ JSON на доску. Старые данные автоматически не удаляются. Архивирование
  цепочек пока не реализовано. Лимиты HTTP/SSE и настройка для общего NAT
  описаны в [инструкции эксплуатации](deploy/README.md#ограничения-первого-размещения).
