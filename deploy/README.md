# Постоянная работа Retro

Комплект рассчитан на закрытый сервис одной команды: один Linux-сервер,
Docker Compose, один Retro с SQLite и Caddy с HTTPS и общим паролем.
Интернет видит только Caddy. Порт приложения не публикуется, метрики закрыты
снаружи. `/readyz` доступен без пароля и возвращает только состояние готовности.

После общего входа Retro проверяет подписанную сессию браузера и список участников
конкретной доски. Ведущий добавляет коллег по ID через кнопку «Добавить участника».
После обновления старые доски открываются ведущему, который заново предоставляет доступ коллегам.
При потере ID ведущего администратор может восстановить управление через CLI.

Интеграция с Jira подключается отдельно: [настройка Jira](JIRA.md),
дополнительный файл `compose.jira.yaml`. Основной запуск без неё не меняется.

## Что потребуется

1. VPS с Ubuntu 24.04 LTS, постоянным SSD и публичным IP. Для первого небольшого
   пилота разумная стартовая конфигурация — 2 CPU, 4 ГиБ RAM и 40 ГиБ диска.
   Это исходная конфигурация, не подтверждённая нагрузочным SLA; ресурсы нужно
   уточнить по измерениям своей команды. Для готового CI-образа выбирайте amd64;
   на arm64 соберите образ на сервере.
2. Домен или поддомен, например `retro.example.org`. В DNS создайте A-запись на
   IP сервера. AAAA нужна только при работающем IPv6. Откройте TCP 80/443,
   UDP 443 для HTTP/3 по желанию; SSH ограничьте своим способом администрирования.
3. Docker Engine и Compose по [инструкции Docker для Ubuntu](https://docs.docker.com/engine/install/ubuntu/).
   Docker должен запускаться при загрузке ОС: `sudo systemctl enable --now docker`.
4. Python 3.9+, restic и внешнее хранилище резервных копий (например S3).
   Проверен restic 0.19.1. На сервере нужен HTTPS webhook получателя уведомлений,
   принимающий JSON `{"text":"..."}`. Пароль restic храните также вне VPS:
   без него восстановить зашифрованный бэкап невозможно.

Внешний мониторинг доступности на другом сервере/сервисе должен проверять
`https://ДОМЕН/readyz` каждую минуту и уведомлять после трёх неудач. Локальный
монитор не сможет сообщить о выключении самого VPS. Настройка внешнего
получателя и DNS выполняется при выборе сервера и домена.

## Первый запуск

Команды далее выполняются администратором на VPS. Репозиторий размещён в
`/opt/retro`; systemd units используют именно этот путь.

```sh
git clone https://github.com/deno-10/retro.git /opt/retro
cd /opt/retro
# Выберите коммит/тег, содержащий этот комплект, после его публикации.
cp .env.example .env
chmod 600 .env
install -d -m 700 deploy/secrets
```

В `.env` укажите настоящий `RETRO_DOMAIN`, `ACME_EMAIL` и уникальный тег
`RETRO_IMAGE`, например `retro:2026-11-12-1`. Пароли в `.env` не нужны.
Сгенерируйте длинный случайный пароль в менеджере паролей, сохраните его там
и введите в интерактивном терминале. При установленном Caddy используйте
`python3 deploy/set-team-password.py`. Скрипт атомарно записывает только
bcrypt-хеш в `deploy/secrets/users.caddy` с правами `0600`. Для временного
туннеля укажите `--file data/sharing/users.caddy`. Для другого пути к Caddy
есть аргумент `--caddy`. При смене пароля перезапустите Caddy.

При установке только через Docker получите хеш интерактивно командой
`docker run --rm -it caddy:2.11.9-alpine caddy hash-password --algorithm bcrypt`.
Запишите строку `team ХЕШ` в `deploy/secrets/users.caddy` с правами `0600`.
Файлы с открытым паролем, включая прежний `data/sharing/access.json`, не нужны.

```sh
docker compose config --quiet
docker compose build --pull retro
docker compose run --rm --no-deps caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
docker compose up -d --no-build --wait --wait-timeout 90
docker compose ps
curl --fail https://ДОМЕН/readyz
```

Caddy получает и продлевает сертификат автоматически; DNS и входящие 80/443
должны работать. Откройте сайт, введите `team` и общий пароль. Убедитесь, что
инкогнито сначала требует общий пароль, а после входа по ссылке на чужую доску
показывает «Доска недоступна». Экспорт, история и SSE этой доски возвращают `404`.
Схема сети `172.30.91.0/24` зарезервирована для backend: при конфликте измените
подсеть, `ip_range`, IP Caddy и `-trusted-proxy` вместе. Динамический диапазон
`172.30.91.128/25` не включает статический IP Caddy `172.30.91.2`, чтобы Retro
не занял его при запуске первым. Нельзя доверять произвольному
`X-Real-IP`/`X-Forwarded-Proto` из интернета.

Retro работает без root, с read-only корнем, ограничениями CPU/RAM/PID,
постоянным томом и ротацией логов. Caddy сохраняет сертификаты в своих томах.
`restart: unless-stopped` поднимает контейнер после падения и перезагрузки хоста.
Метка Docker `unhealthy` сама по себе не перезапускает живой процесс: об этом
сообщит мониторинг, причину нужно проверить в логах.

## Резервные копии и оповещения

```sh
install -d -m 700 /etc/retro /var/lib/retro-ops
cp deploy/ops.example.json /etc/retro/ops.json
chmod 600 /etc/retro/ops.json
```

Заполните `/etc/retro/ops.json`, затем создайте файлы с правами `600`:

| Файл | Содержимое |
|---|---|
| `/etc/retro/restic-repository` | Адрес отдельного хранилища, например `s3:https://s3.provider.example/bucket/retro` |
| `/etc/retro/restic-password` | Случайный длинный пароль шифрования restic |
| `/etc/retro/restic-environment.json` | Например `{"AWS_ACCESS_KEY_ID":"…","AWS_SECRET_ACCESS_KEY":"…"}`; `{}` для backend без этих ключей |
| `/etc/retro/alert-webhook` | Полный HTTPS URL получателя уведомлений |

В S3 используйте отдельный закрытый bucket/префикс и ключ с доступом только
к нему. Нельзя делать bucket публичным. Для других backend задайте параметры
по [документации restic](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html).
`rclone:` допустим только с действительно удалённым хранилищем. Локальная
папка, соседний том или bucket на том же VPS не защищают от потери сервера.

Инициализация выполняется один раз. Для существующего репозитория `init`
пропускается. Следующая команда проверки уведомлений отправляет настоящее
тестовое сообщение настроенному получателю.

```sh
python3 deploy/ops.py init
python3 deploy/ops.py test-alert
python3 deploy/ops.py backup
python3 deploy/ops.py check
install -m 644 deploy/systemd/retro-* /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now retro-backup.timer retro-monitor.timer
systemctl list-timers 'retro-*'
```

Каждый день в 03:00 UTC с разбросом до 15 минут скрипт:

1. Создаёт согласованный `VACUUM INTO` снимок живой SQLite, проверяет её
   целостность и декодирование досок. Нельзя копировать только `retro.db`
   обычным `cp` при работающем WAL.
2. Шифрует и загружает снимок restic во внешнее хранилище.
3. Скачивает **именно этот** снимок, сравнивает SHA-256 и проверяет SQLite.
4. Оставляет 7 дневных, 4 недельных и 6 месячных точек, выполняет `restic check`.
5. Только после всех шагов записывает успешный результат в
   `/var/lib/retro-ops/backup.json`. Временные открытые копии удаляются.

Для снимка и проверки нужно свободное место на диске базы и в `state_dir`:
планируйте запас не меньше нескольких размеров БД. Копии не помещаются в RAM.
Бэкап не включает пароли, DNS и конфигурацию VPS: храните их отдельно.
По умолчанию возможна потеря до суток изменений при полной утрате сервера.
Если это неприемлемо, сократите период таймера и `max_backup_age_hours`.

Монитор каждую минуту проверяет HTTPS, прирост 5xx/429, диск Docker и место
для копий, возраст бэкапа (не более 27 часов), ошибки последней попытки.
После трёх последовательных проблем отправляется уведомление; повторов при
неизменном состоянии нет, восстановление сообщается отдельно. Ошибка доставки
не считается успехом и повторяется на следующей проверке.

```sh
journalctl -u retro-backup.service -n 100
journalctl -u retro-monitor.service -n 100
docker compose logs --tail 100 retro caddy
docker compose exec -T retro wget -q -O - http://127.0.0.1:8080/metrics
```

`/healthz` проверяет работающий процесс, `/readyz` — ещё и чтение БД с
таймаутом. Метрики не содержат ID, текстов и токенов: счётчики HTTP, 5xx,
429, число открытых SSE, время работы и число goroutine.

## Восстановление после потери диска

На чистом VPS восстановите конфигурацию, пароль restic и доступ к хранилищу.
Используйте исходную версию Retro или совместимую более новую. Загрузите
нужный snapshot через restic, указав repository/password файлы и параметры
backend. Получите ID и путь команды `restic snapshots --host retro-production`
и `restic ls ID`. Типовой путь внутри снимка —
`/var/lib/retro-ops/snapshot/retro.db`:

Команды с `$RETRO_IMAGE` требуют предварительно задать эту переменную из
выбранного тега в `.env`; Docker Compose читает файл сам, обычный shell — нет.

```sh
# Настройте RESTIC_REPOSITORY_FILE, RESTIC_PASSWORD_FILE и доступ к backend
# в закрытом окружении администратора; не вставляйте секреты в команды/логи.
restic dump ID /var/lib/retro-ops/snapshot/retro.db > /secure/restore/retro.db
docker run --rm --user 0:0 -v /secure/restore:/restore:ro "$RETRO_IMAGE" verify -data /restore/retro.db
```

Восстанавливайте в **новый пустой том**, сохраняя старый для расследования:

```sh
docker compose stop retro
docker volume create retro_data_restored
docker run --rm --user 0:0 -v /secure/restore:/restore:ro -v retro_data_restored:/app/data \
  "$RETRO_IMAGE" restore -from /restore/retro.db -data /app/data/retro.db
docker run --rm --user 0:0 --entrypoint sh -v retro_data_restored:/app/data \
  "$RETRO_IMAGE" -c 'chown -R 10001:10001 /app/data'
```

Замените `RETRO_DATA_VOLUME` в `.env` на `retro_data_restored`, выполните
`docker compose up -d --no-build --wait`. Проверьте `/readyz`, владельца,
тексты карточек, решения и цепочку ретро. После проверки сделайте новый
внешний бэкап. `restore` откажется перезаписывать существующую БД или путь
со старыми `-wal`/`-shm`/`-journal` — смешивать их со снимком нельзя.

## Обновление, откат и остановка

CI выполняет Go race/vet, браузерные и интеграционные тесты, проверку Caddy,
restic и Compose. При публикации тега `v*` после проверок собирается amd64
образ `ghcr.io/deno-10/retro:ТЕГ` и `:sha-ПОЛНЫЙ_COMMIT`. Это настройка будущих
релизов; наличие workflow не означает, что образ уже опубликован. Для
закрытого GHCR настройте вход на сервере либо соберите образ локально.

Перед обновлением запустите `ops.py backup`, запишите старый тег/дайджест.
Используйте уникальные теги или digest, не изменяйте уже развёрнутый тег.
Для исходников сначала выберите проверенный коммит, задайте новый RETRO_IMAGE
и выполните `docker compose build --pull retro`. Для GHCR используйте
`docker compose pull retro`. Затем:

```sh
docker compose up -d --no-build --wait --wait-timeout 90
curl --fail https://ДОМЕН/readyz
```

Проверьте существующую доску в двух браузерах. Обновление одного экземпляра
даёт короткий перерыв; SSE переподключается. Для отката верните прежний
RETRO_IMAGE и повторите `up`. Текущие изменения не меняют схему БД.
При будущей несовместимой миграции потребуется восстановление предрелизного
снимка в новый том; записи после снимка в нём отсутствуют.

Dependabot следит за Go, npm, Dockerfile и GitHub Actions. Версию и digest
Caddy в `compose.yaml` также обновляйте с проверками; все Docker-образы и
actions закреплены, автоматического обновления запущенного сайта нет.

```sh
docker compose stop                         # остановить, сохранив данные
docker compose start                        # запустить снова
docker compose restart retro                # перезапустить приложение
systemctl disable --now retro-monitor.timer retro-backup.timer  # обслуживание/полная остановка
```

При обслуживании после `start` снова включите таймеры и проверьте свежесть
бэкапа. Не используйте `docker compose down -v` для рабочего сервиса: эта
команда удаляет тома с историей и сертификатами.

## Восстановление ведущего

После обновления со старых браузерных ID или потери cookie участник открывает
Retro и в консоли браузера читает `document.querySelector('meta[name="retro-participant"]').content`.
Это открытый ID для назначения роли. Саму cookie передавать не требуется.
Администратор после бэкапа останавливает приложение, меняет владельца нужной
доски и запускает его снова:

```sh
docker compose stop retro
docker compose run --rm --no-deps retro transfer-owner -data /app/data/retro.db \
  -board ID_ДОСКИ -participant НОВЫЙ_ID
docker compose up -d --no-build --wait
```

Карточки, решения и их авторы не меняются. Владелец меняется только у выбранной
доски; доступ к остальной цепочке при необходимости восстанавливают отдельно.
Для сохранения новых гостевых сессий после потери диска также восстановите прежний `/app/data/retro-session.key` из отдельной защищённой копии (владелец — пользователь Retro, права `0600`). Резервная копия SQLite этого ключа не содержит.

## Ограничения первого размещения

- Один процесс и один локальный SQLite-диск. Несколько реплик требуют общей
  БД и общей доставки событий. Сетевой файловый диск для WAL не подходит.
- На экземпляр: 1000 досок; на доску: 500 карточек, 200 решений, 5000 ключей
  повтора и 4 МиБ JSON. Старые ключи не удаляются, поэтому поздний повтор не
  создаёт дубликат. При исчерпании лимита операций создайте следующее ретро.
  Архивирование и удаление целых цепочек остаётся отдельной функцией; лимит
  досок не означает автоматическое удаление старой истории.
- На IP: 10 API-запросов/с с запасом 200 и 6 созданий досок/мин с запасом 30.
  Создание следующего ретро входит в ту же квоту. Одновременных коротких API
  запросов не более 64; при перегрузке возвращается 429 с Retry-After.
- SSE: 20 соединений на IP, 50 на доску, 200 всего. В офисе за общим NAT
  несколько вкладок расходуют общий лимит. Флаги `-sse-per-ip`,
  `-sse-per-board`, `-sse-total` позволяют увеличить его после измерений.
  Не добавляйте короткий общий WriteTimeout: поток должен оставаться открытым,
  дедлайн ограничивает каждую отдельную запись в SSE.
- Локальный общий вход достаточен для доверенной команды. Для внешних клиентов,
  нескольких организаций и персонального отзыва доступа нужны SSO и права досок.

Перед первым рабочим ретро проверьте: перезагрузку VPS; возврат сайта и
таймеров systemd; перезапуск Retro с открытой доской; восстановление копии в
новом томе; доставку тестового уведомления; внешний сигнал о недоступности VPS.

## Локальные регрессионные проверки

```sh
go test -race ./...
go vet ./...
npm ci
npx playwright install chromium
npm test
npm run test:integration
python3 -m unittest discover -s tests/ops -v
go build -o /tmp/retro-test .
RETRO_TEST_BINARY=/tmp/retro-test CADDY_TEST_BINARY=/путь/к/caddy \
  python3 -m unittest discover -s tests/deployment -v
```

Для последней команды `restic` должен быть в PATH. Она проверяет HTTPS,
пароль, закрытый экспорт/историю/SSE, CSRF, поток событий, перезапуск и реальный
зашифрованный бэкап с восстановлением. Используются отдельные порты и временные
базы. Docker-тест запускается отдельно после `docker build -t retro:ci .`:
`RETRO_CONTAINER_SMOKE=1 python3 tests/deployment/container_smoke.py`.
Ему нужны свободные 80/443; запускайте на отдельном тестовом хосте/CI.
