# Перенос Retro в PaaS и BaaS

Этот комплект готовит код к размещению внутри компании. PaaS запускает Go-сервис,
BaaS (Backoffice as a Service) обеспечивает корпоративный вход и маршрутизацию,
PostgreSQL хранит доски. Ресурсы платформы этим комплектом не создаются.

## Что уже поддерживается

- `RETRO_PROFILE=paas`: HTTP `:8890`, JSON-логи, обязательные PostgreSQL и BaaS.
  Пустые параметры вызывают ошибку запуска; автоматического перехода к SQLite нет.
- `GET /_info` и `/healthz`: жив ли процесс; `GET /readyz`: доступна ли таблица БД.
  `/metrics` содержит Prometheus-метрики экземпляра. Эти четыре пути доступны
  без пользовательского входа; наружу через BaaS их проксировать не нужно.
- Транзакции PostgreSQL сериализуют изменения одной доски. Импорт через
  `Store.CreateMany` и создание следующего ретро атомарны; квота досок общая.
- SSE немедленно получает локальные изменения и раз в секунду сверяет общую БД.
  Закреплять участника за конкретной репликой не требуется. Фоновая проверка
  восстанавливает истёкшие таймеры даже без открытых браузеров.
- BaaS-пользователь определяется по `X-Baas-User-Id` и `X-Baas-Space-Name`.
  Его ID стабилен для одного пространства на разных компьютерах. Подставить
  ведущего через `X-Participant` нельзя. Черновики и история браузера разделены
  по корпоративным аккаунтам. Старая вкладка после смены аккаунта получает 409
  и требует обновления вместо отправки чужого черновика.
  SSE переподключается раз в минуту для повторной проверки сессии шлюзом;
  уже открытый поток может действовать до конца этого интервала.
- Размещение как в корне домена, так и под префиксом `/team/retro`.
  HTML, API, SSE, экспорт, ссылки и статика используют этот префикс.

## Параметры

Все параметры задаются через окружение. Локальный режим по умолчанию сохраняет
прежние `:8080` и `data/retro.db`. Параметры `-addr`, `-data`, `-trusted-proxy`,
`-log-json`, `-sse-*` переопределяют соответствующие значения окружения.

| Переменная | Назначение |
| --- | --- |
| `RETRO_PROFILE` | `local` (по умолчанию) или `paas` |
| `RETRO_ADDR` | Адрес прослушивания; `:8890` в PaaS |
| `RETRO_STORAGE` | `sqlite` или `postgres`; PaaS требует `postgres` |
| `RETRO_DATA` | Путь локального SQLite/JSON, не используется PostgreSQL |
| `RETRO_DATABASE_URL` | Секрет с URL PostgreSQL; обязателен для `postgres` |
| `RETRO_AUTH_MODE` | `local` или `baas`; PaaS требует `baas` |
| `RETRO_BAAS_SPACE` | Точное имя единственного разрешённого пространства |
| `RETRO_TRUSTED_PROXY` | CIDR непосредственного доверенного прокси/sidecar, не `0.0.0.0/0` |
| `RETRO_PUBLIC_ORIGIN` | Внешний origin, например `https://retro.example.test`, без пути и `/` в конце |
| `RETRO_BASE_PATH` | Внешний путь компонента без завершающего `/`; пустой в корне |
| `RETRO_LOG_JSON` | `true`/`false`, в PaaS `true` |
| `RETRO_SSE_PER_IP` / `RETRO_SSE_PER_BOARD` / `RETRO_SSE_TOTAL` | Лимиты соединений на экземпляр: 20 / 50 / 200 по умолчанию |

`RETRO_DATABASE_URL` должен указывать на основной узел PostgreSQL и отдельную БД
Retro. Драйвер поддерживает настройки TLS и URL-кодирование пароля. В контуре
используйте параметры TLS/CA, выданные платформой; `sslmode=disable` ниже нужен
только для локального теста. У каждого экземпляра пул максимум 10 соединений.
Не добавляйте пароль в командную строку, файлы репозитория или логи.

## Порядок переноса после ответа наставника

1. Уточнить команду-владельца, имя PaaS-сервиса, окружение первого запуска,
   пространство и адрес BaaS, LDAP-группу/политику доступа. Отдельно согласовать
   PostgreSQL в STaaS, резервные копии и доступ сервиса к Jira.
2. Создать сервис через `avito service create` с актуальным корпоративным
   шаблоном Go. Сохранить созданные платформой `app.toml`, `auth.toml`,
   `nfr.toml`, `alert.yaml`, `actions.toml`, линтеры, Dockerfile и CI.
   Перенести исходники Retro и адаптировать сборку бинарника `service-entrypoint`.
   Не заменять корпоративный шаблон целиком файлами из GitHub.
3. Подключить PostgreSQL к сервису. Проверить фактические переменные подключения
   в PaaS и настроить секрет `RETRO_DATABASE_URL` для своего окружения.
   Сервис читает этот URL; автоматического преобразования любых переменных STaaS
   в URL в коде нет. При необходимости сделать адаптер в корпоративном шаблоне.
4. Внести значения из `app.toml.fragment` в существующий `[env_vars]`.
   Включить mTLS и разрешить `baas-kong-gateway` по `auth.toml.example`.
   **Заголовки BaaS сами по себе не являются доказательством входа.** Прямой
   ingress к пользовательским путям должен быть закрыт правилами платформы.
   CIDR в Retro ограничивает непосредственного прокси, но не заменяет mTLS.
5. Выполнить миграцию из одноразовой задачи с доступом к БД:

   ```sh
   ./service-entrypoint migrate
   ```

   Она создаёт таблицу `retro_boards` и индекс таймеров, не копирует локальные
   данные. Миграция повторяема и сериализована. Для неё нужны права DDL; рабочей
   роли достаточно SELECT/INSERT/UPDATE таблицы. После миграции запустить
   `./service-entrypoint serve`, проверить `/_info` и `/readyz`.
6. Через мастер BaaS настроить компонент с проксированием HTML существующего
   сервиса (режим Page/SSR), корпоративный вход и политику доступа команды.
   Это не React-компонент с manifest: UI уже отдаёт Go. Совместимость выбранного
   шаблона и мастера с таким размещением проверить в staging.
   Проксировать `/`, `/b/*`, `/static/*` (GET) и `/api/*` (нужные методы, SSE).
   Служебные `/metrics`, `/_info`, `/healthz`, `/readyz` оставить внутренними.
7. Если компонент живёт под `/team/retro`, задать `RETRO_BASE_PATH=/team/retro`.
   Шлюз должен удалять этот префикс: внешний `/team/retro/api/boards` приходит
   в Go как `/api/boards`. Префикс сам по себе не добавляет серверные маршруты.
   Проверить обновление страницы `/b/<id>`, SSE без буферизации и скачивание
   Markdown. BaaS API-компонент добавляет собственный префикс сервиса: не
   смешивать его автоматически с режимом Page/SSR.
8. Запустить две реплики в staging. Провести пробное ретро двумя аккаунтами,
   завершить этап кнопкой и таймером, перезапустить обе реплики, проверить данные.
   Убедиться, что прямой ingress не позволяет обойти вход и политику команды.
9. Подключить стандартные для команды логирование, метрики, алерты и Sentry
   корпоративного шаблона. Сейчас Retro пишет JSON в stdout и отдаёт `/metrics`;
   отправки в Graphite/Sentry и автоматической настройки дашбордов здесь нет.
   Проверить резервное копирование PostgreSQL и восстановление в отдельную БД.
10. Когда staging проверен, подготовить конкретный production-релиз и выкатить
    его принятым в команде способом. Настройку Jira выполнять отдельно после
    получения разрешений и токена; секрет хранить в платформе, не в браузере.
    `RETRO_PUBLIC_URL` для ссылки из Jira задаётся отдельно: полный адрес Retro
    вместе с `RETRO_BASE_PATH`, например `https://retro.example.test/team/retro`.

## Локальные данные и ограничения первого переноса

По умолчанию корпоративный сервис начинает с пустой БД. Старые SQLite-доски
связаны с браузерными ID, а корпоративные — с UUID BaaS и пространством.
Нельзя назначать права по имени автора: оно произвольное. Если нужно перенести
историю, сначала сохранить SQLite-снимок, согласовать соответствие участников
и ведущих, затем выполнить отдельный проверяемый перенос в staging. Команды
`backup`, `restore`, `verify`, `transfer-owner` существующего CLI работают с
SQLite и не предназначены для PostgreSQL. Автоматического переноса истории нет.

Внутри разрешённого BaaS-пространства ведущий добавляет на доску персональные ID коллег.
Retro проверяет состав доски при чтении, экспорте, получении событий и изменении данных.
На этапе записи чужие карточки скрыты даже от других участников доски.
При смене пространства требуется миграция ID участников и ведущих.

В режиме PostgreSQL UI показывает «Подключено» вместо локального числа вкладок:
общий онлайн между репликами пока не считается. Готовность «Я закончил» общая
и хранится в БД. Ограничения запросов/SSE действуют на каждый экземпляр;
общий лимит и ограничения входящего трафика настраиваются на шлюзе.

## Проверка без доступа к платформе

Нужны Go, Node, Chromium Playwright и временный PostgreSQL. Например:

```sh
docker run --rm -d --name retro-pg-test -p 127.0.0.1:55439:5432 \
  -e POSTGRES_USER=retro_test -e POSTGRES_DB=retro_test \
  -e POSTGRES_PASSWORD=local_test_only postgres:17
export RETRO_TEST_POSTGRES_URL='postgres://retro_test:local_test_only@127.0.0.1:55439/retro_test?sslmode=disable'
go test -race ./...
go vet ./...
npm ci
npx playwright install chromium
npm test
npm run test:integration
docker stop retro-pg-test
```

Каждый Go-тест создаёт случайную схему `retro_test_*` и удаляет только её.
Без `RETRO_TEST_POSTGRES_URL` тесты PostgreSQL пропускаются; CI задаёт эту
переменную и запускает настоящую БД. Браузерный тест BaaS поднимает локальный
прокси с фиктивными пользователями, временную SQLite и проверяет UI под
префиксом, стабильность ID, изоляцию черновиков и запрет подмены аккаунта.
Реальные SSO, mTLS, BaaS и STaaS этим тестом не проверяются.

Переносимый образ можно собрать `docker build -f deploy/paas/Dockerfile -t retro:paas .`.
Его запуск без обязательной конфигурации должен завершаться ошибкой.
Для PaaS итоговый образ собирается корпоративным pipeline после адаптации шаблона.
